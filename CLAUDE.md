# Chief of Staff

Особистий Telegram-бот для керування задачами (українська + англійська, текст і голос).
Власник і єдиний продуктовий замовник — Любомир. Спілкування — українською.

## Стек і прод

- Python 3.12, python-telegram-bot 21.x (long polling), OpenAI Responses API (structured outputs, `gpt-4.1`), транскрипція `gpt-4o-mini-transcribe`.
- Postgres у Supabase через transaction pooler (PgBouncer, порт 6543) — prepared statements вимкнені, див. `infrastructure/database/session.py`.
- SQLAlchemy async + asyncpg, міграції Alembic (`alembic/versions/NNNN_*.py`).
- Прод: Railway, EU-регіон, auto-deploy з `main` репозиторію `lt41285/chief-of-staff`. Push у `main` = деплой.
- Лише один інстанс: два процеси з одним токеном дають `telegram.error.Conflict`.
- Часовий пояс — Київ (`services/clock.py: KYIV`). У тестах завжди `FrozenClock`, ніколи реальний час.

## Команди

```bash
.venv/bin/python -m pytest -q          # увесь набір, ~15 с
.venv/bin/python -m chief_of_staff     # локальний запуск (конфліктує з продом, якщо той самий токен)
.venv/bin/alembic upgrade head
railway status / railway deployment list   # потрібен `railway link` у цій папці
```

## Архітектура

`bot` (Telegram-адаптери) → `services` (use-cases) → `models` (Pydantic, без I/O) → `infrastructure` (БД, OpenAI).
Вхід кожного повідомлення: `bot/utterance.py: process_user_utterance` → AI-роутер (`services/intent_router.py`) → детерміноване виконання в сервісах.

## Незмінні принципи

1. **AI інтерпретує, Python виконує.** Жодна write-операція не відбувається без Python-гейту і, де треба, кнопки підтвердження.
2. **Підтвердження дії («створено», «записав», «позначено») формує лише Python після успішного виклику репозиторію.** Вільний текст LLM (`chat_reply`, `phrase`) проходить через `services/write_claim_guard.py`. Кожна нова write-інтеграція (Calendar, Gmail) повинна мати свій Python-форматер, а не покладатися на текст моделі.
3. **Відповіді про дані — тільки з фактів цього ходу** (`services/grounded_reply.py`): ID, кількості, хвилини мають збігатися.
4. **Дати парсяться детерміновано** в `services/deadline_parse.py`, не в AI-екстракції.
5. **Задача створюється лише в наявному проєкті.** Проєкт створюється тільки явною командою.
6. **Не патчити окремі фрази.** Баг з реального діалогу → знайти клас проблеми, виправити механізм, додати регресійний тест, який відтворює саме той ланцюжок повідомлень.
7. **RLS увімкнений на всіх таблицях `public`** (міграція `0011_enable_rls`), доступ ролей `anon`/`authenticated` відкликано. Бот ходить як власник таблиць і RLS обходить. Кожна нова таблиця в міграції: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`. Supabase Data API боту не потрібен.
8. Повідомлення в Telegram ≤ 4096 символів — надсилати через `bot/telegram_text.py: reply_telegram_text`.

## Як працюємо

- Кожен фікс — з тестами. Перед комітом прогнати весь набір.
- Коміт і push (= деплой) — лише коли Любомир прямо просить. Окремі фікси — окремими комітами.
- Звіт після задачі (стандартний блок):
  **Що виправлено** · **Справжня причина** · **Результат тестів** · **Що покрито новими тестами** · **Що НЕ покрито / ризик** · **Системний паттерн** · **Статус деплою** (закомічено? запушено? який коміт на проді?).

## Відомий технічний борг

- Стан розмов, драфтів і підтверджень живе в пам'яті (`InMemory*Store`) — губиться при кожному деплої/рестарті.
- Немає allowlist Telegram-користувачів — будь-хто може писати боту і витрачати бюджет OpenAI.
- Немає CI: тести запускаються лише локально, Railway деплоїть без них.
- `bot/utterance.py` і `services/*_intent.py` обросли регулярками поверх AI-роутера; нові евристики додавати лише як крайній захід.
- Нагадування (`bot/notifier.py`) не розбивають довгі повідомлення; немає кнопки «показати більше» для списків > 20.
